# BUG-090 · El respaldo automático no creaba respaldos y el panel no operaba

Severidad: crítico
Archivo: src/app/api/backup/route.ts
Prueba: tests/api/backup-role-and-filename.test.ts, tests/api/backup-cron.test.ts

## Cómo reproducirlo
Pulsar crear o eliminar desde `/backups`: el navegador no conoce
`BACKUP_API_KEY`, por lo que ambos métodos respondían 401 incluso con sesión
administrativa. Además, `vercel.json` programaba un `GET /api/backup`; Vercel
Cron usa GET con `CRON_SECRET`, pero ese método intentaba listar respaldos con
una cookie de sesión y nunca ejecutaba la creación.

## Qué debería pasar
El panel debe aceptar una sesión `ADMIN` o `SUPER_ADMIN`; el script debe seguir
usando su clave de proceso; y Vercel Cron debe llamar una ruta GET separada que
compare `CRON_SECRET`. Una lectura incompleta de datos no puede guardarse como
si fuera un respaldo válido.

## Corrección aplicada
Se agregó `/api/backup/cron`, se actualizó la programación y se separó la
lógica de exportación. Las operaciones manuales aceptan rol administrativo o
`BACKUP_API_KEY`; el cron exige su secreto propio. Una falla al leer leads o
documentos cancela el archivo, y una segunda ejecución del mismo día reemplaza
la exportación diaria en vez de fallar por nombre duplicado.

Referencia: [seguridad de Vercel Cron](https://vercel.com/docs/cron-jobs/manage-cron-jobs#securing-cron-jobs).

## Límite importante
Esto es una exportación JSON de filas de leads y documentos guardada en el
mismo proyecto Supabase. No contiene esquema SQL, usuarios, otras tablas ni los
archivos físicos de Storage, por lo que no reemplaza un respaldo completo y
probado fuera del proyecto.

## Acción operativa pendiente
Una persona con acceso debe configurar `CRON_SECRET`, confirmar el bucket
privado `backups`, ejecutar la ruta una vez y ensayar restauración. También debe
confirmar el respaldo administrado de Supabase o un `pg_dump` externo.
