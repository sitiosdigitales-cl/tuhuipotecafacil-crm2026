# BUG-129 · Las actividades fallidas quedaban visibles como guardadas

Severidad: alta
Archivo: `src/lib/contexts/ActivityContext.tsx`
Prueba: `tests/state/activity-mutation-persistence.test.tsx`

## Comportamiento observado

El contexto agregaba una actividad con un ID local antes de llamar a la API y
la conservaba aunque la respuesta fuera fallida. No comprobaba el estado HTTP
ni usaba el ID persistido. Además, la ficha de cliente reemplazaba el historial
por un arreglo vacío y sus acciones de contacto llamaban una función sin efecto.

## Comportamiento esperado

El historial debe mostrar solo actividades devueltas o confirmadas por la API,
con su identificador persistido. Si el registro secundario falla, la acción
principal puede continuar, pero la interfaz debe informar que la bitácora no se
guardó. La ficha debe leer el historial real del lead.

## Impacto

La interfaz podía mostrar evidencia que desaparecía al recargar y, al mismo
tiempo, omitir contactos realizados desde la ficha. Esto impedía confiar en la
cronología operativa de cada caso.

## Corrección

El contexto ahora espera una respuesta satisfactoria, normaliza el objeto del
servidor y propaga fallos. La API devuelve camelCase e incluye metadata. La
ficha usa el proveedor real y todos los llamadores manejan el fallo de registro
sin confundirlo con el resultado de la acción principal.
