# BUG-128 · Una creación fallida aparecía como lead guardado

Severidad: crítica
Archivo: `src/lib/contexts/LeadContext.tsx`
Prueba: `tests/state/lead-mutation-persistence.test.tsx`

## Comportamiento observado

Si `POST /api/leads` fallaba o no respondía, el contexto fabricaba un lead con
un ID local y lo agregaba a la interfaz. Las tres pantallas cerraban el
formulario y mostraban éxito sin esperar la respuesta. Incluso en éxito, la
actividad posterior usaba el ID temporal, no el UUID creado por el servidor.
Actualizar, eliminar y mover etapas también restauraba estado en silencio sin
informar el fallo a quien había iniciado la operación.

## Comportamiento esperado

Una mutación debe confirmarse solo después de una respuesta satisfactoria. El
estado cliente debe incorporar el objeto y el identificador persistidos por el
servidor; ante un fallo, no debe alterar los datos confirmados, debe conservar
el formulario y mostrar que la operación no terminó.

## Impacto

Una persona podía continuar trabajando sobre una ficha inexistente, registrar
actividad contra un ID que no existe o creer que una edición o eliminación se
había guardado. Al recargar, los cambios desaparecían.

## Corrección

El contexto elimina el fallback local, devuelve el lead persistido y propaga
los errores de crear, actualizar y eliminar. La API responde camelCase e
incluye la asignación estable. Los formularios esperan la operación, permanecen
abiertos si falla y las pantallas confirman solo después del servidor. La
asignación guarda el ID estable del usuario y el arrastre permite desasignar.
